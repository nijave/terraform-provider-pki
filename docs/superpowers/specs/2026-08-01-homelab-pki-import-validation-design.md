# homelab-pki import validation — design

Date: 2026-08-01
Status: approved for planning

---

## 1. Background

`terraform-provider-pki`'s own design doc
(`docs/superpowers/specs/2026-07-25-terraform-provider-pki-design.md`, §14)
lists as a deferred follow-up: rewrite `homelab-pki` (a Python reconciler at
`vmubtkube-a/homelab-pki/reconcile/` that shells out to `openssl`/`cfssl` to
mint per-device mTLS client certs for Home Assistant) onto this provider,
deleting the reconciler, stripping cfssl/openssl/python from its Dockerfile,
and collapsing its two-phase apply (Python renders `secrets.auto.tfvars.json`,
then a separate plain-OpenTofu apply writes `kubernetes_secret`s) into one
provider-driven apply.

That whole reconciler exists because vanilla OpenTofu can't express "keep an
arbitrary N of existing certs" without a pre-step. A provider with real
CRUD/state removes that need — `for_each` over a device list can drive
resource lifecycle directly. But before designing the harder half (Dockerfile
rewrite, Job/CronJob collapse, provider distribution into the cluster), this
spec covers proving the provider actually handles *this* CA and *these*
certs correctly, entirely locally.

Current live data (namespace `homelab-pki`, read via `kubectl` for this
design): a self-signed RSA-4096 CA (`subject=issuer=OU=apps, O=homelab`,
serial `4D71D760878EB0A8831CE2E1D6028F61F1FC7D5F`, valid 2025-02-26 to
2045-02-26, delivered from Bitwarden, never generated by this code) and 5
device leaf certs (`pki-kara-iphone-2000`, `pki-nick-desktop-2001`,
`pki-nick-ipad-2002`, `pki-nick-xps-2003`, `pki-pixel7-2004`), matching
`homelab-pki/config.hcl`'s `users` map exactly.

While gathering this data we reproduced a known bug directly: the current
CRL's issuer is encoded `O=homelab, OU=apps`, but the CA's actual
subject/issuer is `OU=apps, O=homelab` — reversed RDN order. Consequently:

```
$ openssl verify -CAfile pki-ca.crt -crl_check -CRLfile pki-crl.pem pki-nick-desktop-2001.crt
error 3 at 0 depth lookup: unable to get certificate CRL
```

cfssl's `gencrl` is reconstructing the issuer name attribute-by-attribute
instead of copying it byte-for-byte from the CA, so CRL matching fails.
`internal/pki`'s `sign.go`/`crl.go` are documented as building certs from
`RawSubject`/`RawIssuer` specifically for byte-exact reproducibility, so the
new provider is expected to avoid this — but that must be proven, not
assumed, since it's the one correctness property production revocation
depends on.

## 2. Goal

Prove, entirely locally (no cluster writes, no provider publishing), that
`terraform-provider-pki` can:

1. Import the real CA and all 5 real device certs/keys with **zero plan
   drift**.
2. Issue a new device cert against the imported CA.
3. Generate a CRL that **actually validates** against the CA (fixing the
   OU-order bug) and that **actually reflects revocation** when a serial is
   revoked.

This is the gating step before designing the cluster cutover (Dockerfile,
Job/CronJob, `kubernetes_secret` output, provider distribution) — those are
explicitly out of scope here (§5).

## 3. Harness layout

New directory in this repo (not in `vmubtkube-a`, since this validates the
provider, not the eventual production module):

```
migration/homelab-pki-import/
  main.tf              # terraform{} + provider "pki" {} block
  ca.tf                 # pki_certificate_authority.ca (config matched to the real CA)
  devices.tf            # 5x named pki_private_key + pki_certificate blocks
  new-cert.tf            # pki_private_key/pki_certificate["migration-test"] (not imported, freshly issued)
  crl.tf                # pki_crl.ca
  import.sh              # sequenced `tofu import` commands, one per resource
  fetch-secrets.sh        # kubectl get secret ... | base64 -d > fetched-secrets/*.pem
  verify.sh               # openssl checks encoding success criteria (§4)
  fetched-secrets/        # gitignored: real CA/device cert+key PEMs pulled via kubectl
  terraform.tfstate*      # gitignored: local backend, never the kubernetes backend
  FINDINGS.md             # written after the run: what happened, any diffs, any bugs found
```

`.gitignore` covers `fetched-secrets/`, `*.tfstate*`, `*.crt`, `*.key`, `*.p12`
— real key material never gets committed, even to a scratch directory.

**Provider wiring:** no version of this provider has been published to the
OpenTofu registry yet (no GitHub releases exist; `.goreleaser.yml` is still
`draft: true`). Rather than solve that here, the harness uses Terraform's
`dev_overrides` (`TF_CLI_CONFIG_FILE` pointing `registry.opentofu.org/nijave/pki`
at a `go build`'d binary). This bypasses version constraints and prints a
warning on every plan/apply, which is expected and fine for a local dev loop.
How the real cluster Job obtains the provider is deferred to the follow-on
cluster-cutover spec.

**Backend:** local `terraform.tfstate` file. Nothing here uses the
`kubernetes` backend or talks to the live cluster except read-only
`kubectl get secret` to fetch source material.

## 4. Import mechanics and test steps

Uses `terraform import` (the documented mechanism — `docs/resources/{private_key,certificate_authority,certificate}.md` already show this exact scenario, down to using `nick-ipad`/`homelab-pki` as the worked example), not declarative `import {}` blocks.

**CA** (`pki_certificate_authority.ca`): `private_key_pem` is set directly in
the resource config (the schema holds it inline — no separate key resource
for a CA), along with subject/validity/key-usage/serial attributes matched
to the real CA's decoded values. Then:
```
tofu import pki_certificate_authority.ca 'file://fetched-secrets/pki-ca.crt'
```
`tofu plan` afterward must show **zero diff**. Any diff pinpoints exactly
which config attribute doesn't match the real CA (subject field order,
serial encoding, validity, etc.) — that mismatch *is* the useful output of
this step, not a failure to route around.

**Each device** (`pki_private_key.device["<name>"]` +
`pki_certificate.device["<name>"]`, explicit named blocks — not `for_each`,
so a stuck import stays isolated to one block instead of being buried in an
instance key):
1. Import the private key: `tofu import 'pki_private_key.device["nick-ipad"]' 'file://fetched-secrets/nick-ipad.key'`.
2. Derive `public_key_pem` from that key (`openssl pkey -pubout`) to satisfy
   `pki_certificate`'s exactly-one-of `csr_pem`/`public_key_pem` requirement,
   and set it, plus `parent_certificate_pem`/`parent_private_key_pem` (the
   CA's PEMs), in the `pki_certificate` block's config.
3. Import the cert: `tofu import 'pki_certificate.device["nick-ipad"]' 'file://fetched-secrets/nick-ipad.crt'`.
4. `tofu plan` must show **zero diff**.

Repeat for all 5 devices.

**New-cert test:** `pki_private_key.device["migration-test"]` +
`pki_certificate.device["migration-test"]`, signed by the imported CA,
applied fresh (no import). Confirms normal issuance against this specific
real CA works, not just that import round-trips existing data. Decode with
`openssl x509 -text` and confirm subject/SAN/EKU match the same identity
shape as the other devices.

**CRL test:** `pki_crl.ca` signed by the imported CA, `revoked = []`
initially. Verify with the exact command that currently fails in
production:
```
openssl verify -CAfile fetched-secrets/pki-ca.crt -crl_check \
  -CRLfile <generated-crl>.pem fetched-secrets/nick-desktop.crt
```
Must return `OK`. Then add the `migration-test` device's serial to
`revoked`, re-apply, regenerate, and confirm `openssl verify` now reports
that cert specifically as **revoked** (not merely that the CRL parses).

## 5. Success criteria

All must hold:

1. CA imports with zero plan diff.
2. All 5 device private keys + certificates import with zero plan diff.
3. `migration-test` issues cleanly against the imported CA with the expected
   subject/SAN/EKU shape.
4. Generated CRL passes `openssl verify -crl_check` against the CA and a
   real leaf cert.
5. Revoking `migration-test`'s serial and regenerating the CRL causes
   `openssl verify` to report it as revoked.

Any failure gets written up in `FINDINGS.md` (what broke, why, whether it's
a provider bug or a config mismatch on our side) rather than silently worked
around — surfacing exactly this class of problem is this spec's entire
purpose.

## 6. Out of scope (deferred to a follow-on cluster-cutover spec)

- Provider distribution for the real Job/CronJob (filesystem mirror baked
  into the image vs. publishing a real registry release).
- Dockerfile/Job/CronJob rewrite — removing cfssl/openssl/python.
- `kubernetes_secret` output wiring (needed downstream, not exercised here —
  local backend only).
- PKCS#12 bundle password fix (currently hardcoded `"password"`), CRL→Contour
  `HTTPProxy` wiring, a CI build step for the image — pre-existing
  `homelab-pki` pain points, not this spec's job.
- Root-causing *why* cfssl's `gencrl` reverses the RDN order. We only need
  to confirm the new path avoids the bug (§4's CRL test), not explain the
  old one.
